Run Collabase in a Kubernetes cluster with the Helm chart that ships in the release package. This guide takes you from an empty namespace to a running installation, and then covers the choices a cluster operator makes: certificates, your own image registry, an external database, scaling and backups.

If you have a single Linux server, the [installation with Docker](/installation) is simpler and fully supported. You do not need Kubernetes to run Collabase.

## At a glance {#at-a-glance}

| | |
|---|---|
| **Result** | Collabase runs in its own namespace, reachable over HTTPS at your address. |
| **Time** | The install itself takes a few minutes. The first start takes longer while the images download and the database is prepared. |
| **You need** | Cluster access with `kubectl` and Helm, a DNS name for Collabase, and the release package. |
| **Edition** | All editions. Activate an Enterprise licence key after the install. |

## Requirements {#requirements}

| | Requirement |
|---|---|
| **Cluster** | Kubernetes 1.26 or later, on `amd64` nodes |
| **Tools** | `kubectl` and Helm 3.10 or later on the machine that installs |
| **Capacity** | At least 4 GB RAM and 2 vCPU free in the namespace for a small team. See [System requirements](/admin/system-requirements#cpu-and-memory). |
| **Storage** | A default storage class with `ReadWriteOnce` volumes, about 45 GB in total |
| **Ingress** | An ingress controller. The chart is written for nginx and sets nginx annotations. |
| **Pod security** | A namespace at `privileged` or `baseline` with the defaults. For `restricted` set `securityContext.enabled: true`; the plug sandbox still does not start there, see [Pod security](#pod-security). |
| **Certificates** | cert-manager with a ClusterIssuer, or your own TLS certificate as a secret |
| **Images** | Access to `ghcr.io`, or your own registry that holds copies of the images |
| **Address** | A DNS name that points at your ingress, for example `collabase.yourcompany.com` |

The full list of ports, outbound connections and images is on [System requirements](/admin/system-requirements). Send that page to the team that runs your cluster.

## What runs in your cluster {#what-runs-in-your-cluster}

The chart creates six workloads, each with one instance, and two one-time jobs.

| Workload | Kind | Purpose | Memory limit | CPU limit | Volume |
|---|---|---|---|---|---|
| **App** | Deployment | Web interface, API and background jobs | 2.75 GB | 2 | 10 GB uploads, 10 GB shared home, 1 GB documents |
| **PostgreSQL** | StatefulSet | Database with `pgvector` | 4 GB | none | 20 GB |
| **Redis** | StatefulSet | Queue for background jobs | none, data capped at 256 MB | none | 2 GB |
| **Document processor** | Deployment | File conversion and PDF export | 1.5 GB | 1 | none |
| **Collaboration relay** | Deployment | Live editing, can be turned off | 768 MB | 1 | none |
| **Plug sandbox** | Deployment | Isolated execution of automation plugs, can be turned off | 2 GB | 2 | 2 GB |
| **Migration** | Job | Database changes, runs on install and before every upgrade | | | |
| **Seed** | Job | Creates the first administrator, runs on install only | | | |

The memory the scheduler reserves is 512 MB for the app, 1 GB for the database and 256 MB for the sandbox. The chart also sets small CPU requests: 250m for the app, 100m each for the document processor, the sandbox and the collaboration relay. The database and the queue set none. If your namespace has a resource quota or a limit range that demands more, set them in your values file, see [Adjust resources](#adjust-resources).

<Note>
  With the default settings the app and its volumes run as a single instance. To run more than one instance, see [Scale out](#scaling-out).
</Note>

## Install {#install}

*Phase 1 of 3. Next: [Verify the installation](#verify).*

<Steps>
  <Step title="Unpack the release package">
    Download `collabase-deployment-<version>.zip` from the [download page](https://collabase.ch/en/download) and unpack it. The chart is in `deployment/helm`.
  </Step>
  <Step title="Write a values file">
    Keep your settings in a file, not in a long command. Create `collabase-values.yaml`:

    ```yaml title="collabase-values.yaml"
    app:
      url: https://collabase.yourcompany.com
      adminEmail: admin@yourcompany.com

    ingress:
      host: collabase.yourcompany.com
      className: nginx
      tls:
        clusterIssuer: letsencrypt-prod
    ```

    `app.url` is the public address people open. It must match `ingress.host`.
  </Step>
  <Step title="Install the chart">
    ```bash
    helm install collabase ./deployment/helm \
      --namespace collabase --create-namespace \
      -f collabase-values.yaml
    ```

    The chart installs the images of the release it belongs to. All passwords and keys are generated on the first install.
  </Step>
  <Step title="Wait for the first start">
    The database is prepared by a one-time job. The application can answer with errors until it finishes.

    ```bash
    kubectl get jobs -n collabase --watch
    ```
  </Step>
  <Step title="Read the administrator password">
    ```bash
    kubectl get secret collabase -n collabase \
      -o jsonpath='{.data.adminPassword}' | base64 -d
    ```

    Sign in at your address with the administrator email from your values file and this password. You are asked to choose a new password.
  </Step>
</Steps>

<Note>
  **Create the first admin yourself.** The chart starts a first-run job that creates an admin from `secrets.adminPassword`. Set `migrations.seed: false` to skip it: the installation then starts without an admin and the first visit to `/setup` creates the admin, the title and the language. The default is `true`.
</Note>

## Verify the installation {#verify}

*Phase 2 of 3. Previous: [Install](#install). Next: [Activate the licence and add people](#next-steps).*

<Check>
  **Checkpoint.** All pods are `Running` and ready, both jobs are `Complete`, and the address answers with `"status":"ok"`.

  ```bash
  kubectl get pods,jobs -n collabase
  curl https://collabase.yourcompany.com/api/health
  ```

  If something is not ready, see [Troubleshooting](#troubleshooting).
</Check>

## Certificates {#certificates}

The ingress terminates HTTPS. Choose one way to get a certificate.

| Option | When | Settings |
|---|---|---|
| **cert-manager** | You run cert-manager and have a ClusterIssuer | `ingress.tls.clusterIssuer: <name>`. The certificate is stored in the secret `collabase-tls`. |
| **Your own certificate** | Your organization issues certificates | Create a TLS secret named `collabase-tls` in the namespace and leave `clusterIssuer` empty. Change the name with `ingress.tls.secretName`. |
| **TLS ends before the cluster** | A load balancer or gateway in front already holds the certificate | `ingress.tls.enabled: false` |

```bash title="Use your own certificate"
kubectl create secret tls collabase-tls -n collabase \
  --cert=fullchain.pem --key=privkey.pem
```

Create the secret before the install so the ingress finds it at the start.

## Use another ingress controller {#other-ingress}

The chart sets nginx annotations and defaults to the class `nginx`. For another controller, set `ingress.className` and check these three points:

- **Upload size.** Allow request bodies of at least 32 MB. The chart sets the nginx annotation `proxy-body-size` from `ingress.maxBodySize`. Other controllers need the same limit in their own way, through `ingress.annotations`.
- **WebSockets.** Live collaboration connects to `/collab` on the same address. The controller must pass WebSocket upgrades through.
- **Sign-in rate limit.** The chart adds a second ingress that limits sign-in attempts with an nginx annotation. Set `ingress.authRateLimit.enabled: false` for a controller that ignores it, and limit `/api/auth/callback` in your own gateway.

The Docker installation also limits all other requests per client address. The chart does not. Set a general request limit in your gateway or ingress if you need one.

To manage the routes yourself, set `ingress.enabled: false`. Route `/` to the service `collabase-app` on port 3000, and `/collab` to the service `collabase-collab` on port 1234. The service names start with your release name.

## Use your own image registry {#own-registry}

Many clusters cannot pull from `ghcr.io`. Copy the images into your registry, then point the chart at them.

<Steps>
  <Step title="Copy the images">
    Copy these images at the version of your release package. The tag is the version number without a leading `v`.

    ```text
    ghcr.io/collabase/collabase
    ghcr.io/collabase/collabase-document-processor
    ghcr.io/collabase/collabase-collab
    ghcr.io/collabase/collabase-sandbox
    pgvector/pgvector:pg16
    redis:7-alpine
    ```
  </Step>
  <Step title="Set the repositories">
    ```yaml title="collabase-values.yaml"
    image:
      repository: registry.yourcompany.com/collabase/collabase
    documentProcessor:
      image:
        repository: registry.yourcompany.com/collabase/collabase-document-processor
    collab:
      image:
        repository: registry.yourcompany.com/collabase/collabase-collab
    sandbox:
      image:
        repository: registry.yourcompany.com/collabase/collabase-sandbox
    postgresql:
      image: registry.yourcompany.com/library/pgvector:pg16
    redis:
      image: registry.yourcompany.com/library/redis:7-alpine
    ```

    The tags stay empty. Each image uses the version of the chart.
  </Step>
  <Step title="Allow the cluster to pull">
    If your registry needs a login, create a pull secret in the namespace and list it in `imagePullSecrets` in your values file, for example `imagePullSecrets: [{ name: ghcr-pull }]`. The chart sets it on every pod.

    ```bash
    kubectl create secret docker-registry registry-login -n collabase \
      --docker-server=registry.yourcompany.com \
      --docker-username=<user> --docker-password=<token>
    kubectl patch serviceaccount default -n collabase \
      -p '{"imagePullSecrets":[{"name":"registry-login"}]}'
    ```
  </Step>
</Steps>

A cluster with no route to the internet at all can also use the [air-gapped installation](/admin/airgapped-installation) approach for the images.

## Use your own database {#own-database}

Use a managed PostgreSQL by turning off the bundled one:

```yaml title="collabase-values.yaml"
postgresql:
  enabled: false
  externalUrl: postgresql://collabase:<password>@db.yourcompany.com:5432/collabase
```

The database must be PostgreSQL 16 or later with the `vector` extension. The migration job runs `CREATE EXTENSION IF NOT EXISTS vector`, which needs a privileged user. If your provider restricts it, enable the extension once in the provider's console. See [System requirements](/admin/system-requirements#database).

The connection pool is sized for you. Each app process gets 80 % of `max_connections` divided by the number of processes, at most 100 each. Override it with `database.connectionLimit`.

## Manage secrets {#secrets}

On the first install the chart generates every password and key and stores them in the secret `collabase`. Later upgrades keep the existing values.

<Warning>
  Never delete the secret `collabase`. It holds the key that encrypts stored credentials such as mail and integration logins. If it is lost, those credentials cannot be recovered and must be entered again. `helm uninstall` removes the secret too. Include it in your backup.
</Warning>

Tools that render the chart without a live connection to the cluster, such as `helm template` in a GitOps pipeline, cannot read the existing secret. They would generate new keys on every render. In that case create the secret yourself and reference it:

```yaml title="collabase-values.yaml"
secrets:
  existingSecret: collabase-secrets
```

The secret needs these keys: `postgresPassword`, `nextauthSecret`, `adminPassword`, `pdfPrintToken`, `automationEncryptionKey`, `encryptionKey`, `mailEncryptionKey`, `databaseUrl`, `collabSharedSecret`, `sandboxSharedSecret` and `engineTokenSecret`. With S3 storage add `s3AccessKeyId` and `s3SecretAccessKey`. Generate each value as a random string of at least 32 characters.

If you move an existing Docker installation to Kubernetes, copy `ENCRYPTION_KEY`, `MAIL_ENCRYPTION_KEY`, `AUTOMATION_ENCRYPTION_KEY`, `NEXTAUTH_SECRET`, `PDF_PRINT_TOKEN` and `POSTGRES_PASSWORD` from the `.env` file into the `secrets` section of your values file on the first install.

## Adjust resources {#adjust-resources}

Every workload takes its limits from the values file. Raise them in the same place:

```yaml title="collabase-values.yaml"
app:
  resources:
    requests:
      cpu: "500m"
      memory: 512Mi
    limits:
      cpu: "2"
      memory: 2816Mi
```

The same `resources` block exists for `documentProcessor`, `collab`, `sandbox` and `postgresql`. These are the CPU requests the chart sets by default:

| Workload | Value | CPU request |
|---|---|---|
| **App** and dedicated worker | `app.resources.requests.cpu` | `250m` |
| **Document processor** | `documentProcessor.resources.requests.cpu` | `100m` |
| **Collaboration relay** | `collab.resources.requests.cpu` | `100m` |
| **Plug sandbox** | `sandbox.resources.requests.cpu` | `100m` |

Without a CPU request Kubernetes would reserve the whole limit as the request, so these small values let the scheduler place the pods without holding cores they do not use. To size the whole installation for your team, see [Sizing & scaling](/admin/scaling). The database settings under `postgresql.tuning` assume a node with at least 8 GB of RAM. Lower `shared_buffers` and `effective_cache_size` on a smaller one.

## Plug sandbox {#plug-sandbox}

The sandbox runs automation plugs from third parties in isolation. It starts with every install. It needs a security profile on the node to isolate plugs fully. Without the profile it still starts, reports `degraded` on its health check and runs no third-party plug. Everything else works as before.

| Choice | Settings |
|---|---|
| **No third-party plugs** | `sandbox.enabled: false`, or leave the defaults and accept `degraded`. |
| **Full isolation, chart loads the profiles** | `sandbox.loadProfiles: true`, `sandbox.apparmorProfile: Localhost`, `sandbox.seccompProfile: Localhost`. Loading starts a privileged pod on every node, so it is off by default. |
| **Full isolation, you install the profiles** | The profile files are in `deployment/helm/files`. Install them on each node, then set the two profile values to `Localhost`. |

`Localhost` for AppArmor needs Kubernetes 1.30 or later. Network policies keep the sandbox away from the database and the queue. Your cluster must enforce them.

## Scale out {#scaling-out}

Running more than one app instance needs two things. The chart refuses to render without them.

1. **S3 file storage.** With cluster volumes, a second instance cannot see files the first one stored. Set up a private bucket first, see [File storage](/admin/file-storage).
2. **A dedicated worker.** Background jobs move to their own single instance so they run exactly once.

```yaml title="collabase-values.yaml"
replicaCount: 3
workers:
  separate: true
storage:
  driver: s3
  s3:
    bucket: collabase
    endpoint: https://your-s3-endpoint
    accessKeyId: <key>
    secretAccessKey: <secret>
```

With S3 storage the app pods carry no volumes and update without downtime. For the database and the other parts, see [Sizing & scaling](/admin/scaling#scaling-beyond-one-server).

### Roll out without downtime {#rollout}

These values change how the app instances update and stop. Every default keeps your installation as it is.

| Value | Default | What it does |
|---|---|---|
| `app.rollingUpdate` | `false` | With S3 storage, `true` replaces one instance at a time and never takes one away before its successor is ready. |
| `app.spreadAcrossNodes` | `false` | `true` forces the instances onto different nodes. Each revision is spread on its own (`matchLabelKeys: [pod-template-hash]`), so a rolling update cannot leave the old and the new instance together on one node. Kubernetes applies `matchLabelKeys` from version 1.27. |
| `workers.replicas` | `1` | Number of worker instances, with `workers.separate: true`. |
| `nodeSelector` | `{}` | Restricts every pod, except the plug sandbox profile loader, to matching nodes. |
| `redis.auth.existingSecretKey` | empty | Name of a key in your own secret (`secrets.existingSecret`). Redis then requires that password. |
| `app.clientIpHeader` | empty | Name of the request header that carries the visitor's address, for example `cf-connecting-ip` behind Cloudflare. |
| `migrations.argoCd` | `false` | `true` lets Argo CD run the database migration and the first-run setup instead of Helm hooks. The pre-upgrade backup job is then not created. |

Instances get 40 seconds to finish open requests when they stop, workers 60 seconds. With more than one instance the chart also creates a disruption budget, so draining a node never takes all instances away at once. With Redis, the request limit counts across all instances.

## Pod security {#pod-security}

Many platforms enforce the Kubernetes Pod Security Standards on a namespace, or run a policy engine such as Kyverno or OPA Gatekeeper. The chart was checked against a server-side dry run in a namespace that enforces `restricted`.

| Level | Result |
|---|---|
| **Privileged** | Everything starts. |
| **Baseline** | The app, database, queue, collaboration relay and document processor set nothing that baseline forbids. The plug sandbox does not start with its default `apparmorProfile: Unconfined`, because baseline allows only the default or a `Localhost` profile. Install the profiles on the nodes and set `Localhost`, or turn the sandbox off. `sandbox.loadProfiles: true` starts a privileged pod and is rejected, so install the profiles yourself. |
| **Restricted** | The app, worker, database, queue, relay and document processor and the migrate, seed and backup jobs meet it with `securityContext.enabled: true`, see below. The default is off. The plug sandbox does not: it needs an AppArmor and a seccomp profile that `restricted` forbids with the default `Unconfined` AppArmor profile, and `sandbox.loadProfiles: true` starts a privileged pod. Turn the sandbox off in such a namespace (`sandbox.enabled: false`, third-party plugs then do not run) or ask for an exemption for it. |

With `securityContext.enabled: true` (off by default) the chart runs every workload except the sandbox as a non-root user with the ID of its image, without privilege escalation, with all capabilities dropped and the default seccomp profile. The root filesystem stays writable. Override single keys under `podSecurityContext` and `containerSecurityContext` of a workload if a platform assigns user IDs itself or an image or volume does not work with these values (`app`, `collab`, `documentProcessor`, `redis`, `postgresql`, `migrations`, `backup`). Volumes of the database and the queue are set up for the image users with `fsGroup`; on a new Kubernetes version with an old storage driver that ignores it, make the volume writable for the user ID 999.

A policy engine may also require resource requests and limits, images from approved registries or pinned versions. The chart pins every image to the release by default and sets memory requests, but sets CPU requests only if you add them, see [Adjust resources](#adjust-resources).

## Network connections {#network-connections}

The chart ships one network policy, for the plug sandbox. If your cluster denies traffic by default, allow these connections. All ports are TCP.

| From | To | Port | Purpose |
|---|---|---|---|
| Ingress controller | App | 3000 | Web interface and API |
| Ingress controller | Collaboration relay | 1234 | Live editing on `/collab` |
| App | Database | 5432 | Data |
| App | Queue | 6379 | Background jobs |
| App | Document processor | 8000 | File conversion and PDF export |
| App | Plug sandbox | 8100 | Plug execution |
| Plug sandbox | App | 3000 | Plug calls back into Collabase |
| Collaboration relay | App | 3000 | Saving documents |
| Migration and seed jobs | Database | 5432 | Database setup |
| App | Outside the cluster | 443 and as configured | Sign-in provider, mail, S3, AI provider, connected services |

The app pods and the worker pod need the same connections. The sandbox may reach the internet except private address ranges, and DNS. Add your pod network to `sandbox.networkPolicy.internetExceptCidrs` if it is not in a private range.

## Scheduling and platform settings {#scheduling}

The chart has settings for `nodeSelector`, `imagePullSecrets` and `app.spreadAcrossNodes`. It has none for `tolerations`, `affinity`, priority class, pod annotations or extra environment variables. Use these ways instead:

- **Pull secrets:** set `imagePullSecrets`, see [Use your own image registry](#own-registry).
- **Scheduling and annotations:** let Helm pass the rendered manifests to a post-renderer such as Kustomize with `helm install --post-renderer`. The post-renderer adds the fields you need to the pods.
- **Node pools:** if your platform assigns nodes per namespace, set it on the namespace.

## Monitoring {#monitoring}

Collabase has no metrics endpoint for Prometheus. Monitor it with probes, cluster metrics and the health address.

| Check | Address or source | Meaning |
|---|---|---|
| **App liveness** | `/api/health` on port 3000 | The process runs. The status stays `200`, with `"status":"degraded"` and a list when a background feature needs attention. |
| **App readiness** | `/api/health/ready` on port 3000 | The app can reach its database. A pod that fails it is taken out of the service. |
| **Document processor** | `/health` on port 8000 | The service runs. |
| **Plug sandbox** | `/health` on port 8100 | Answers `200`, and `degraded` when the jail cannot start. |
| **Logs** | Output of each pod, in JSON | Set the level with `app.logLevel`. |

Alert on pods that restart or stay unready, on failed jobs, on volumes that fill up, on a certificate close to expiry and on `degraded` in the health response. See [Health check](/api/health).

## Availability {#availability}

With the default settings every part runs once. A restart of the app, the database or the queue interrupts the service for the time the pod needs to start, and nothing fails over to another copy.

| Part | What you can do |
|---|---|
| **App** | Run more instances with S3 file storage and the dedicated worker, see [Scale out](#scaling-out). |
| **Database** | Use an external PostgreSQL with failover, see [Use your own database](#own-database). The bundled database is a single pod. |
| **Uploads** | Store them in S3 and keep versions in the bucket. |
| **Queue** | A single pod with its data on a volume. Jobs survive a restart. |

## Update {#update}

Unpack the new release package and upgrade with the same values file:

```bash
helm upgrade collabase ./deployment/helm -n collabase -f collabase-values.yaml
```

The chart installs the version it belongs to, so the new package moves every image to the new release. Migrations run before the new version starts. The full procedure, with backup, checks and rollback, is on [Updates](/admin/updates#kubernetes).

## Back up and restore {#backup}

Back up three things: the database, the uploaded files and the secret `collabase`. The chart can also take a database dump before each upgrade:

```yaml title="collabase-values.yaml"
backup:
  enabled: true
```

The dump goes to its own volume and the last seven days are kept. Turn the option on one upgrade before the one you want protected, because the volume is created after the checks of that first upgrade. This does not replace your regular backup. See [Backup & Restore](/admin/backup).

If your storage supports volume snapshots, snapshot the volumes for uploads, documents and the shared home directory. A snapshot of the running database is only crash-consistent. For the database, rely on a dump. With S3 storage, turn on versioning in the bucket. Test a restore on your test system before you need it.

Restore a database dump into the existing installation, then run `helm upgrade`. Do not restore into a new `helm install`. A fresh install runs its first-time setup and would write on top of your restored data.

## Remove Collabase {#uninstall}

```bash
helm uninstall collabase -n collabase
```

This removes the workloads, the secret and the volumes for uploads, documents and the sandbox. The volumes of the database and the queue are kept. Back up the secret and your data first. Delete the remaining volumes with `kubectl delete pvc` only when you want the data gone for good. This cannot be undone.

## Kubernetes versions {#kubernetes-versions}

The chart is written for Kubernetes 1.26 or later. A list of the versions we tested against each release is not published yet. Ask us for the current state before you plan.

| Needs | Kubernetes version |
|---|---|
| The chart | 1.26 or later |
| AppArmor profile set through the pod field `appArmorProfile` (`sandbox.apparmorProfile: Localhost`) | 1.30 or later |

Helm 3.10 or later is required. A newer minor version of Kubernetes needs no change to the chart as long as the APIs it uses stay available: `apps/v1`, `batch/v1` and `networking.k8s.io/v1`.

## OpenShift and other distributions {#openshift}

Managed Kubernetes services and hybrid platforms built on upstream Kubernetes need nothing beyond the [requirements](#requirements). The chart has not been tested on OpenShift. These are the points that differ there. Tell us if you use it, and we verify the installation with you.

| Topic | Standard Kubernetes | On OpenShift |
|---|---|---|
| **Routing** | Ingress | Use a Route. Set `ingress.enabled: false` and route `/` to the service `collabase-app` on port 3000 and `/collab` to `collabase-collab` on port 1234, with WebSockets allowed. |
| **Volume group** | `app.fsGroup: 1001` | The platform assigns the group, and a fixed value is rejected. Set `app.fsGroup: null`. |
| **User IDs** | The images run as fixed IDs | The default policy runs pods with an ID from the namespace range. Whether the images start under an arbitrary ID is not verified. Your security team decides whether the service account may use a policy with fixed IDs. |
| **Plug sandbox** | Profiles for seccomp and AppArmor | OpenShift uses SELinux instead of AppArmor. Set `sandbox.enabled: false`. Third-party plugs then do not run. |
| **Images** | Registry of your choice | Copy the images into your registry, see [Use your own image registry](#own-registry). |

## Troubleshooting {#troubleshooting}

| What you see | Cause | What to do |
|---|---|---|
| The install fails with a job error | The migration job could not prepare the database | Read the log: `kubectl logs job/collabase-migrate -n collabase`. The most common cause is a missing `vector` extension on an external database. |
| Errors for the first minute or two after install | The setup jobs are still running | Wait, then check `kubectl get jobs -n collabase`. |
| A pod stays in `ImagePullBackOff` | The cluster cannot pull the image | Check the repository and tag, and the pull secret. See [Use your own image registry](#own-registry). |
| A pod stays `Pending` | No node has the memory or storage, or no storage class exists | `kubectl describe pod <name> -n collabase` names the reason. |
| Uploads fail with a permission error | The storage class ignores the group setting of the pod | Check that your volumes honor `fsGroup`, or make them writable for the user with ID 1001. Change the group with `app.fsGroup`. |
| Live editing does not connect | The ingress blocks WebSocket upgrades on `/collab` | See [Use another ingress controller](#other-ingress). |
| The sandbox reports `degraded` | The security profile is not loaded on the node | See [Plug sandbox](#plug-sandbox). The rest of Collabase is not affected. |
| The helm render fails with a message about replicas | More than one instance without S3 and a worker | See [Scale out](#scaling-out). |
| The install failed, and after the repair there is no administrator | The seed job runs after a successful install only (`post-install`), so a failed install never ran it | Fix the cause first. On a fresh install with no data to keep, run `helm uninstall collabase -n collabase`, delete the remaining volumes of the database and the queue with `kubectl delete pvc` (they hold the old passwords), and install again. Otherwise start the seed job by hand: `helm template collabase ./deployment/helm -n collabase -f collabase-values.yaml --show-only templates/migrate-job.yaml > seed.yaml`, then `kubectl apply -f seed.yaml`. `kubectl` reports an error for the migration job that already exists, which you can ignore. |

Collect `kubectl get pods -n collabase` and the log of the failing pod or job before you contact support at [collabase.featurebase.app](https://collabase.featurebase.app/en).
