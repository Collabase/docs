Live collaboration lets several people edit the same page at the same time. Everyone sees the others' changes appear as they are typed, along with each person's cursor and a row of avatars showing who else is on the page.

It works on pages, blog posts and whiteboards.

<Note>
  Live collaboration is **on by default**. A new install has it running, and an existing install picks it up with the next update. An administrator can [turn it off](#turning-it-off). Pages then return to single-writer mode: one person edits, and the **Save conflict** dialog appears if someone else saved in the meantime.
</Note>

## How it works {#how-it-works}

When two or more people open the same page, their edits are merged continuously. Nobody holds a lock, and nobody has to coordinate saving. Everyone can type at once, and every change reaches everyone else within a fraction of a second.

- **Character by character.** Each keystroke is sent to the other editors immediately. You watch other people's text appear as they write it, not after they save.
- **No conflicts.** When two people edit the same sentence at the same time, both changes are kept. Nobody's work is overwritten.
- **Cursors.** Each collaborator's cursor is shown in their own color and labelled with their name, so you see where someone is working.
- **Presence avatars.** The people currently on the page appear as a row of avatars at the top right of the page, left of the status badge. You see them whether you are editing or reading.

## Who appears {#who-appears}

Anyone who has the page open is part of the session, both people who edit and people who only read. A reader sees live changes and other people's cursors but cannot type until they click **Edit**.

Access is unchanged: a person joins the session only for a page they are already allowed to open. Access is also checked again every minute while the page is open. If an administrator deactivates someone's account, or their right to read or edit the page is withdrawn, they are removed from the session within about a minute. If only the right to edit is withdrawn, they are disconnected and can reopen the page as a reader.

## How changes are saved {#saving}

Live sync between people needs no save button. Storing the content happens automatically, on two independent tracks:

| What | When it is saved |
|---|---|
| **Live sync between people** | Instantly, on every keystroke |
| **The shared session document** | Automatically, about 10 seconds after the last edit |
| **The page content and its version** | Automatically, about 1.5 seconds after you stop typing, or at once when you click the save button. Whiteboards save about 5 seconds after you stop drawing. |

Because changes reach the others instantly and are stored shortly after, closing the tab right after a burst of typing is safe. Each save of the page content also creates an entry in the [version history](/docs/version-history).

## How many people {#how-many}

There is no fixed limit. Because changes merge automatically, a page handles dozens of simultaneous editors. At roughly a hundred people editing one page at the same moment, the cursor traffic becomes the practical ceiling. Normal team use stays far below it.

## What runs, and what it costs {#what-runs}

Live collaboration adds one service, the **collaboration relay**, which the installer starts and the reverse proxy already routes to. You do not configure anything to switch it on; it runs after an install or an update.

The relay is a single lightweight process. Budget roughly **200 to 500 MB of RAM** for it, depending on how many people edit at once. Because it is on by default, it is already counted in the **4 GB minimum** for a server. If your server is short on memory and you do not need collaborative editing, turning it off brings the minimum back down to 2 GB. See [Sizing & scaling](/admin/scaling) to size for your team.

<Note>
  If the relay is unreachable, because it is stopped, out of memory or still starting, pages fall back to single-writer editing on their own. A failing relay never blocks editing.
</Note>

## Turning it off {#turning-it-off}

Collaboration is controlled by one setting: `COLLAB_RELAY_URL`. Clearing it turns collaboration off and stops the relay on the next run.

<Steps>
  <Step title="Clear the relay address">
    In your `.env` file, set `COLLAB_RELAY_URL` to an empty value:

    ```bash
    COLLAB_RELAY_URL=""
    ```
  </Step>
  <Step title="Re-run the installer or updater">
    Run `bash update.sh` (or `bash install.sh`). The relay is stopped and pages return to single-writer editing. On Kubernetes, set `collab.enabled: false` in your values file and upgrade the release instead.
  </Step>
</Steps>

Existing page content is unaffected. It is stored the same way whether collaboration is on or off, so you can turn it off and back on at any time.

<Warning>
  `COLLAB_SHARED_SECRET` in your `.env` proves that edits and presence come from your own Collabase. It must stay identical for the application and the relay. The installer and updater generate it for you: do not change it, share it or reuse it elsewhere.
</Warning>
